# win32 — 制約サンドボックスVMで32ビットWindowsソフトウェアを動かす

GPUなし・約1.5コア・数GBメモリという制約の強いLinuxサンドボックスVM上で、レガシーな32ビットWindowsアプリケーション／ゲームを、ユーザーモードエミュレーションと互換レイヤで実行するための環境構築と実測記録のプロジェクトです。

## アーキテクチャ

- **QEMU (user-mode)** — x86 32ビットバイナリの命令変換
- **Wine 11.21 (32-bit)** — Windows API互換レイヤ
- **q32sup** — 独自の監督プロセス（ptrace/seccomp）。ELF32バイナリの execve のみを傍受し、透過的にエミュレーションへ橋渡しします。TOCTOU耐性のあるターゲット固定（memfd／内容検証つきディスクモード）、終了ステータスの正確な伝播を備えます
- **仮想オーディオ** — PulseAudio の仮想シンク経由で音声を実際に供給し、供給率（delivery ratio）を定量化します
- **仮想GPUパス** — virgl によるホスト側レンダリング（Mesa llvmpipe との比較実測つき）

ゲームやアプリ本体には一切手を入れず、すべての対策を環境側（エミュレータ／互換レイヤ／仮想デバイス／フォント）で完結させるのが設計原則です。

## 実測ハイライト

- **エミュレータのバージョン効果はタイトル依存**：フリーウェアのアクションゲーム『洞窟物語』では QEMU 7.2.22 が 10.0.2 の約9倍のテキスト描画速度を示した一方、別の描画エンジンを使う市販タイトル群では 7.2.22 は起動に失敗し、10.0.2 が正解でした。「新しい／古い」ではなくタイトルごとの実測が必要、というのが中心的な知見です
- **監督プロセスの比較**：q32sup と PRoot を同一条件で比較し、システムコール多用ワークロードで約61倍の差を実測。PRoot 配下では Wine がエラーを出さずに無言で終了する事象も確認しました
- **音声の供給率は競合が支配する**：VMを単独で使うと供給率 1.000（欠落ゼロ）を維持できる一方、並行負荷があると 0.56〜0.67 まで低下することを対照実験で確認しました
- **描画の切り分け**：部分転送（ダーティ領域のみの Present）最適化は実測で効果が認められず、コストの所在はゲスト側GLパイプラインの完了待ちであることを特定しました
