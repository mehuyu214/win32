win32 — 制約サンドボックスVMで
32ビットWindowsソフトウェアを動かす

ユーザーモードQEMU ＋ Wine ＋ 独自スーパーバイザによる、レガシー32ビットWindows互換環境の構築と実測

GPUなし・約1.5コア・数GBメモリという制約の強いLinuxサンドボックスVM上で、レガシーな32ビットWindowsアプリケーション／ゲームを実行するための互換環境の構築記録です。対象ソフトウェア本体には一切手を入れず、すべての対策を環境側（エミュレータ／互換レイヤ／仮想デバイス／フォント）で完結させるのが設計原則です。このページ自体に解説を完結させています。

1. どうやって動かすか — アーキテクチャ

三層で構成します。

  • QEMU（ユーザーモード） — x86 32ビットのゲストバイナリを命令変換しながら直接実行します。システム全体を仮想化するのではなくプロセス単位で変換するため軽量ですが、ゲストのシステムコールは変換層を通ってホストのカーネルに届きます。
  • Wine 11.21（32ビット版） — Windows APIをLinux上で再現する互換レイヤ。ゲストのPEバイナリはこの上で「Windowsプログラム」として振る舞います。
  • q32sup（独自の監督プロセス） — ptraceとseccompで子プロセスを監督し、ELF32バイナリの execve だけを傍受してエミュレーション側へ橋渡しします。64ビットの通常プロセスは素通りさせるため、混在したプロセスツリーでも32ビット部分だけが自動的に変換されます。

描画はソフトウェアレンダリング（Mesa llvmpipe）またはホスト側レンダリングサーバ（virgl）へ、音声は仮想オーディオデバイス（PulseAudioの仮想シンク）へ接続します。実ハードウェアのGPUやサウンドデバイスは存在しないため、どちらも「仮想デバイスを構築して実際に機能させる」ことが必須でした。

2. q32sup の設計 — 監督プロセスの勘所

子プロセスの execve を横取りする方式には古典的な落とし穴がいくつもあります。本プロジェクトで実際に踏んで、対策したものです。

  • TOCTOU（検査と実行の間の差し替え） — パス文字列だけを信用して実行すると、検査後にファイルが差し替わる余地があります。対策として実行対象を memfd に固定するか、内容ハッシュ（FNV-1a）を検証して再利用するディスクモードを使い、「検査したバイト列そのもの」を実行します。
  • 長いパス・特殊文字 — シェル経由の起動は引用符まわりで壊れやすいため、パスは安全にクォートし、677文字のパスでも通ることをテストで確認しています。
  • 「エラーを出さない成功」バグ — 初期実装には、子プロセスが最初の停止前に異常終了すると、親がそれを成功として報告してしまうバグがありました。失敗が無言で消えるのは、明示的にクラッシュするより検出が難しく質が悪い。現在は子の終了ステータスを正確に伝播し、テストで担保しています。
  • 代替方式との比較（PRoot） — 同じ監督役を PRoot で担う構成と比較実測しました。システムコールを多用する処理（getpid 20万回）で中央値 89 ms 対 5,412 ms、約61倍の差。さらに PRoot 配下では入れ子の exec がエラーを出さずに何も実行せず終了し、Wine は何も作らないまま終了コード0で終わる事象を確認しました。検出できない失敗を返す方式は、この用途には使えません。

3. 描画スタック — GLが「無い」ように見える理由

  • ベンダ登録の欠落 — 当初、32ビット用 sysroot に libpciaccess.so.0 と libtinfo.so.6 が欠けており、Mesa の glvnd ベンダが登録されず、OpenGL が存在しないように見えていました。不足ライブラリを揃えて依存を閉じさせると EGL 1.5 / Mesa が正常に立ち上がり、ピクセルフォーマット失敗はゼロになりました。「壊れている」ように見える問題の多くは、実は依存の欠落です。
  • llvmpipe と virgl — ソフトウェア描画（llvmpipe）は確実に動きますが重く、ホスト側で描く virgl は高速な反面、起動条件が繊細です。実際に、64ビットの virgl サーバに32ビット用ドライバパスが環境変数経由で混入し、サーバが起動しない障害がありました。クリーンな環境で起動するのが要点です。
  • コストの所在 — 画面転送（Present）の最適化として「変化した領域だけを送る」方式を実装して測りましたが、効果は認められませんでした。切り分けの結果、1フレーム約250 msのコストの本体は転送ではなくゲスト側GLパイプラインの完了待ちでした（転送単体は2〜8 ms）。直観と異なる場所にボトルネックがある、というのが実測で得た教訓です。

4. 音声スタック — 「鳴っている」ことをどう証明するか

音声は PulseAudio の仮想シンク（48 kHz / float32）を構築し、ゲストの音声をそこへ流します。鳴っているかどうかは勘ではなく、供給率（delivery ratio）で測ります：録音した音声の実効長と壁時計時間の比から、期待された音声が欠落なく届いた割合を算出する指標です（1.000 = 欠落ゼロ）。

  • 競合が支配的要因 — VMを単独で使うと供給率は 1.000 を維持できますが、別の重い処理を並行させると 0.56〜0.67 まで低下することを対照実験で確認しました。音声品質を決める最大の変数は、音声設定そのものより「他に何が走っているか」でした。
  • ドライバ経路の切り分け — Wine の音声ドライバには winepulse と winealsa（＋ALSA→Pulseプラグイン）の経路があり、診断ツール上は鳴るのにゲーム内では鳴らない、といった経路依存の差が出ます。どの段階で初期化が失敗しているかを、プローブの戻り値レベルまで追って切り分けました。

5. 計測方法 — 数字の作り方

  • 映像の滑らかさ — 録画を 20 fps で分割し、フレーム間の変化を点数化します。ただしピクセル完全一致のハッシュ方式は、静止画に近い場面でもノイズで過大評価になる（静止したタイトル画面で理想値の2倍近い値が出た）ため撤回し、160×90 グレースケールに縮小して平均絶対差が閾値（0.05）を超えた場合のみ「変化」と数える方式（v2）に統一しました。平均値だけでなく分布（中央値、ゼロ秒の本数）で報告します。
  • A/B の規律 — 比較は同一タイトル・同一区間・同一設定で行い、既存の知見で「効くはず」と分かっている修正は、測る前に先に適用します（既知の最適でない構成をわざわざ測らない）。
  • 画面証拠主義 — 成功の判定はログではなく、画面表示と操作の実証（スクリーンショット、実際に進むストーリー、実際に鳴る音声）で行います。

6. 実測結果

エミュレータのバージョン効果はタイトル依存（非単調）

フリーウェアのアクションゲーム『洞窟物語』でタイトル画面のテキスト描画速度を測りました。QEMU 10.0.2 では約0.55〜0.60文字／秒、7.2.22 では5文字／秒以上、約9倍の差です（タイトル到達も約9分→約1分）。ところが同じ 7.2.22 は、別の描画・音声エンジンを使う市販タイトル群では起動初期に失敗し（Wine の起動過程で異常終了）、10.0.2 では正常に動作しました。高速化の定説はタイトルごとに検証が必要で、本プロジェクトの中心的な知見です。

その他の実測

  • CSMT（コマンドストリーム多スレッド化） — 『洞窟物語』のテキスト描画指標では、無効／有効のいずれでも測定誤差の範囲で差が認められませんでした。
  • フォント — 日本語グリフの欠落（いわゆる「□」表示）は、10,250グリフ／書体のサブセットフォントを7書体分生成して環境側に導入することで解消し、画面で可読性を確認しました。
  • 他者の主張の検証（DOSBox-X） — 外部から寄せられた DOSBox-X（PC-98モード）に関する3件の不具合報告を、同一ビルド（2024.03.01）と自作のテストプログラムで検証しました。「出力が終了時までフラッシュされない」は再現（ただし別マシンモードでも起きるため DOSBox-X 自体の挙動と判定）。「約164 KBで出力が止まる」「時計が00:00で止まる」は再現しませんでした（320〜480 KBの出力が完走、時計は実時間どおり進行）。他者の報告は仮説として扱い、自前の実測で裏を取るまで採用しない、という運用の実例です。

7. 失敗パターンの分類 — 環境側で解けたもの

対象ソフトウェアを一切変更せず、環境側の対策で解決した代表例です。

  • 入力が一切届かない — ウィンドウマネージャが無い X 環境では、タイトル画面がフォーカスを得られず入力を全て無視する。→ ウィンドウマネージャ（twm）を常駐させることで解決。
  • WGLコンテキスト作成直後の違法命令（c000001d） — ホストCPUの拡張命令（AVX2）を含むコードをゲストが実行して落ちる。→ QEMU の CPU モデルを max,-avx2 に制限して解決。
  • 使い古したプレフィックスの汚染 — 長期間使い回した Wine プレフィックスはパス解決が再帰的に壊れるなどして再現性のない失敗をする。→ 新規プレフィックス＋絶対パス起動を原則化。
  • 日本語の文字化け — フォント代替の設定ミスとフォント自体の欠落が原因。→ 代替マップの修正とサブセットフォント導入で解決（6節）。

8. 既知の限界・未解決

  • QEMU 7.2.22 で一部のタイトル群が起動に失敗する内部機構は、システムコールレベルの計装まで踏み込めていないため未特定です（発生箇所と再現条件は特定済み）。
  • 汎用ランチャ経由のゲーム内音声は QEMU 10.0.2 では実証済みですが、7.2.22 では初期化に失敗します。これも機構は未特定です。
  • 本VMの実効容量は約1.5コアであり、得られた絶対速度はこの制約下の値です。通常のPC環境への一般化には、別途の検証が必要です。
